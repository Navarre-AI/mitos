# Mitos against a standard FileMaker search

Mitos 1.1.0, run 2026-11-22, on the bundled sample data (288 records: people, organizations, products). 196 cases, 182 of them answerable without AI. Generated by `npm run bench`.

## What is being compared

- **FileMaker, Quick Find:** every word must match the start of a word in some field, accents and case ignored, all words required, results in record order with no ranking, one table at a time. A typo finds nothing.
- **FileMaker, developer-built find** (used for ranges, dates, `==`, `*`): `900...1500`, `>=`, partial dates like `5/2019`, wildcards. It needs the right field and the right syntax.
- **Mitos:** the deterministic search (exact words, close spelling, name list, typed numbers, ranges, dates, phones, emails). No AI unless noted.
- **A favour to FileMaker:** every case is given the correct table. A real user on the wrong layout finds nothing. Mitos searches all tables and has to put the right one up front.
- **Position** means: for FileMaker, the place in the unsorted found set; for Mitos, the place in the merged list across all tables (up to 20 rows read). Mitos shows 5 rows per table by default.
- The FileMaker side is a model written from the Claris Help pages, not FileMaker itself. See the open questions at the end.

## How FileMaker was set up (read this first)

FileMaker got the best case a developer could set up, every time:

- **The right table.** Each search ran on the one table that holds the answer. A real user has to be on the right layout first; on the wrong one, FileMaker finds nothing. Mitos searched every table at once.
- **The right field and syntax** for ranges, dates and operators (`900...1500` in price, `5/2019` in a date field, `==` in full_name). A real user has to know both.
- **No ranking needed.** With 288 records most found sets are one or two records, so FileMaker's record order rarely costs it anything here. In a real file it would.

So FileMaker's numbers below are a ceiling, and Mitos's are what a user gets typing into one box.

## Where Mitos wins, ties and loses

- **Wins:** typo: one letter wrong (10/10), typo: letters swapped (9/9), typo: letter missing (10/10), typo: phonetic (9/10), nicknames (14/16), partial words (1/14), extra or wrong word (12/14), numbers (1/14), dates (4/18), phones (2/11), emails (1/9), cross-table (1/9), meaning (AI) (13/16). These are the cases FileMaker cannot do at all: typos, nicknames, a wrong or extra word, phones and dates typed in another style, and queries that need meaning.
- **Ties:** exact names (26/26), typo: phonetic (1/10), nicknames (2/16), partial words (13/14), extra or wrong word (2/14), numbers (11/14), dates (14/18), phones (9/11), emails (8/9), cross-table (8/9), meaning (AI) (3/16), non-Latin (6/6), find operators (4/4). For exact names, word starts, and well-formed emails or phones, Quick Find already finds the record. The difference is order: FileMaker gives record order, Mitos puts the best record first.
- **Loses:** numbers (2/14). See the work list below.

Things to keep in mind when reading the numbers:

- FileMaker was handed the right table and the right field for ranges. Real users are not.
- This sample has 288 records. A found set of 40 in a real 100,000 record file is far larger, so FileMaker's "found set size" here is flattering to it and Mitos's "position 1" is the number that scales.
- Mitos's Position 1 is measured in the merged list across tables. Where the right person is first in their own table but an organization (matched through an employee's name) sits above, Position 1 loses and "Position 1 in its own table" does not. This is the known table-order issue from `npm test`.
- Many FileMaker "found" cases land far down an unsorted list. Compare Position 1 and Top 3, not Found alone.
- The cases were written by one person (the author of the benchmark) who knows Mitos. Typos were picked as a real user might make them, not tuned to Mitos, but expect some bias toward what Mitos does.
- 1 of FileMaker's hits come only from the sample's note column. Check sample-data for query text left in notes.
- Chinese records were not added to the sample (it would change ids and counts the `npm test` cases rely on). The Greek and Cyrillic records already in the sample are used.

## FileMaker model: open questions

- Word breaks: apostrophes, dots and @ are treated as word separators (so `Hank` finds `Hank's` and `matt.navarre@example.com` splits into four words). FileMaker's index rules vary by field language; not checked against a live file.
- A typed value with several parts (`773-9565`, an email) is matched generously: each part must start some word in the record. Real FileMaker may be stricter or looser.
- Quick Find on a date field with a bare year (`2019`) is modelled as matching that whole year. The Help describes partial dates for Find mode; Quick Find's handling was not confirmed.
- Quick Find on a number field is modelled as an exact number match (`45` finds price 45, not 450).
- Dates are read month first with `/`, `-` or `.` separators; `19.3.2019` and month names find nothing. A system set to day first would read some of them differently.
- No related-table text in Quick Find (Mitos joins employee names into organizations). A layout with a portal could change that.
- Position in the found set is record creation order (CSV order here). A real layout may have a saved sort.
